# Metrics Reference

The load balancer exposes Prometheus text-format metrics from `GET /metrics` on the admin listener (see [`operations.md`](operations.md) for how to enable and secure that listener). This page documents every metric registered in [`lb-metrics`](../crates/lb-metrics/src/lib.rs): its exact name, type, labels, and the code path that updates it. Every metric listed here is updated by production code; the "Suggested alerts" section at the end uses them directly.

All metric names use the `lb_` prefix baked into the metric name itself (there is no separate registry-wide prefix). Counters are Prometheus counters (monotonic, `_total` suffix), gauges are instantaneous values, and histograms use one of two fixed bucket sets defined in [`lib.rs`](../crates/lb-metrics/src/lib.rs).

## Histogram buckets

Every histogram in this process (`lb_request_duration_seconds`, `lb_upstream_duration_seconds`, `lb_tls_handshake_duration_seconds`) shares the same 15 exponential buckets, generated by `exponential_buckets(0.001, 2.0, 15)`:

```
0.001, 0.002, 0.004, 0.008, 0.016, 0.032, 0.064, 0.128, 0.256, 0.512,
1.024, 2.048, 4.096, 8.192, 16.384   (seconds)
```

The buckets are dense from 1ms to a few hundred ms, where p99 latency for a healthy proxy lives, and reach out to ~16s to still bound pathological tail requests.

## Label-cardinality bounds

Every label value in the exposition comes from a fixed, code-known set — never from a client-supplied header, path, or cache key. This is enforced by a test in [`lib.rs`](../crates/lb-metrics/src/lib.rs) that fails if any label name outside an explicit allowlist appears in the exposition. Specifically:

- `listener` and `backend` come from configuration (operator-controlled, not client-controlled).
- `status`, `outcome`, `layer`, `reason`, `phase`, `result`, `rule` are fixed enums with 2-4 possible values each.
- `peer` on `lb_cluster_future_skew_rejections_total` is bounded to 64 distinct peer labels; the 65th and subsequent distinct peer node IDs seen in a merge are folded into a single `peer="other"` overflow label, so a churning or spoofed cluster cannot grow this series unboundedly. See `MAX_SKEW_PEER_LABELS` and `OVERFLOW_PEER_LABEL` in [`counters.rs`](../crates/lb-cluster/src/counters.rs). `lb_cluster_peer_sync_total` and `lb_cluster_auth_failures_total` bound their `peer` label differently: only IPs listed in `cluster.peers` appear, and every other source is labeled `unknown`.
- `cert` (on `lb_tls_certificate_expiry_timestamp_seconds`) is an operator-chosen certificate name from `[[listeners.tls.certificates]]`, never the client-supplied SNI hostname.
- `le` is Prometheus's own histogram bucket-boundary label, bounded by the fixed bucket count above.

There is no label anywhere for client IP, request path, cache key, or SNI hostname.

## Requests

### `lb_requests_total` — counter

Labels: `listener`, `protocol` (`http1` | `http2`), `status` (`2xx` | `3xx` | `4xx` | `5xx`).

Incremented once per completed HTTP response, classified by `StatusClass::from_code` in [`handles.rs`](../crates/lb-metrics/src/handles.rs) and recorded from the single call site in `lb_proxy::service::handle` after the response is produced. `protocol` reflects the HTTP version hyper negotiated on the connection (not anything a client can assert), resolved once via `req.version()`. A TCP (L4) listener holds these counters like any other listener but never increments them — it forwards bytes, not HTTP requests. There is no `unknown` status value; every response falls into exactly one of the four classes.

### `lb_request_duration_seconds` — histogram

Labels: `listener`.

Observed once per completed HTTP response, in `lb_proxy::service::handle`, measuring wall-clock time from request arrival to response availability (end-to-end, as the client experiences it — not backend-only latency, see `lb_upstream_duration_seconds` below).

### `lb_active_connections` — gauge

Labels: `listener`.

### `lb_connections_total` — counter

Labels: `listener`.

Both are maintained for every listener. For an HTTP or HTTPS listener they are updated in `drive` ([`lib.rs`](../crates/lb-server/src/lib.rs)) once per accepted connection that reaches request serving (after admission, the PROXY header and the TLS handshake), with a drop guard decrementing `lb_active_connections` when the connection ends however it ends. For a TCP listener they are updated at the start of `handle_connection` in [`session.rs`](../crates/lb-tcp/src/session.rs). `lb_connections_total` counts connections, not requests: one HTTP/1.1 keep-alive or HTTP/2 connection carries many requests.

## Connections and timeouts (edge hardening)

### `lb_connections_rejected_total` — counter

Labels: `listener`, `reason` (`max_connections` | `max_per_ip`).

Incremented in `serve_listener` in [`lib.rs`](../crates/lb-server/src/lib.rs): `max_connections` when the listener's global connection-permit semaphore has no permits available at the moment `accept()` would otherwise be called (checked before accepting, so an attacker cannot force an accepted-then-dropped connection); `max_per_ip` when a newly accepted connection's source IP is already at its per-IP cap.

### `lb_request_timeouts_total` — counter

Labels: `listener`, `phase` (`header` | `body` | `upstream_body`).

`phase="body"` is incremented in `lb_proxy::service::handle_inner` when reading the request body exceeds `body_read_timeout` (the client receives `408 Request Timeout`). `phase="header"` is incremented when a connection is closed because the client did not send its request head in time: for HTTP/1.1 when hyper's `header_read_timeout` fires, and for HTTP/2 when `FirstByteDeadline` expires before the client's first byte. A write-side stall (`write_timeout_ms`) is not counted here. `phase="upstream_body"` is incremented when a backend's streamed response body goes longer than `response_body_idle_timeout_ms` without sending anything, and the client's response is aborted.

## Backends, health, and circuit breaking

See [`health-checking.md`](health-checking.md) and [`load-balancing.md`](load-balancing.md) for the mechanisms behind these metrics.

Every metric in this section is labeled per backend and exists for statically configured and DNS-discovered backends alike. When a DNS-discovered backend leaves the resolved set, all of its series in this section are removed from the exposition, so autoscaling churn does not accumulate stale `backend` label values.

### `lb_backend_healthy` — gauge

Labels: `listener`, `backend`.

Set from exactly one place: the active health-check loop, `spawn_active_checker` in [`active.rs`](../crates/lb-healthcheck/src/active.rs), each time a probe completes (`1` healthy, `0` unhealthy). This reflects only the active probe's verdict ("administratively healthy"). It does **not** reflect circuit-breaker state or outlier-detector ejections — a backend can show `lb_backend_healthy 1` while `lb_backend_circuit_state` is `1` (open) or while the outlier detector has stopped sending it traffic; there is currently no dedicated metric for outlier-detector ejections at all. Check both gauges together, and see `lb-healthcheck`'s outlier detector (`outlier.rs`) for the mechanism this gauge does not cover.

### `lb_backend_circuit_state` — gauge

Labels: `listener`, `backend`. Values: `0` closed, `1` open, `2` half-open.

Set from `lb_proxy::service::handle_inner` in two places: once per request, at the top of the handler, refreshing every backend in the resolved pool from its `CircuitBreaker::state()` (so an idle backend's gauge only updates when a request actually touches that backend's pool); and again immediately after a forward attempt succeeds or fails, so a breaker that just tripped or just recovered is reflected within the same request burst rather than waiting for the next one.

### `lb_backend_requests_total` — counter

Labels: `listener`, `backend`, `outcome` (`success` | `failure` | `timeout`).

Incremented once per forward attempt in `handle_inner`: `success` on any response the backend returned (including a 5xx — this counts transport success, not application success; see `lb_requests_total` for the client-visible status), `timeout` when the forward exceeded `forward_timeout`, `failure` on any other connect/transport error.

### `lb_upstream_duration_seconds` — histogram

Labels: `listener`, `backend`.

Observed only on a successful forward (the `success` branch above) — a timed-out or failed attempt never contributes an observation, so this histogram's count will be lower than `lb_backend_requests_total{outcome="success"}` plus the failed/timeout outcomes combined; it measures latency of responses that came back, not attempts.

## Rate limiting

See [`rate-limiting.md`](rate-limiting.md) for the GCRA and cluster-wide algorithms these metrics describe.

### `lb_ratelimit_rejected_total` — counter

Labels: `listener`, `layer` (`local` | `cluster`).

`local` is incremented wherever the per-node GCRA limiter denies a request or TCP connection (`lb_proxy::service::handle_inner` and `lb_tcp::session::handle_connection`). `cluster` is incremented in `handle_inner` when the cluster-wide budget (see `lb-cluster`) denies admission — checked only after the local limiter has already admitted the request.

### `lb_ratelimit_tracked_keys` — gauge

Labels: `listener`.

Set by the rate-limit sweeper after every sweep (every 30 seconds) to the number of distinct keys the listener's limiter tracks. Watch it against `rate_limit.max_tracked_keys`: a value pinned at the cap means new clients are sharing the overflow bucket.

### `lb_ratelimit_cluster_convergence_bound` — gauge

Labels: `listener`.

Set once, at listener wiring time (not on a ticker), in [`wiring.rs`](../crates/lb-server/src/wiring.rs), from `lb_cluster::convergence_over_admission_bound(rate_per_sec, sync_interval_ms, peer_count)`. It is a static, per-listener worst-case bound on how many requests the cluster-wide limiter can transiently over-admit while gossip is converging, not a live counter — it does not change at runtime. Absent a `[cluster]` block for the listener, this gauge is never resolved to a nonzero value (the code path that sets it only runs when both a cluster node and cluster config are present).

## Cluster / gossip

See [`cluster-coordination.md`](cluster-coordination.md) for the CRDT counter-merge and gossip protocol.

### `lb_cluster_future_skew_rejections_total` — counter

Labels: `peer`.

The only cluster-gossip counter that is actually wired up. Incremented in `CounterStore::merge` in [`counters.rs`](../crates/lb-cluster/src/counters.rs) whenever a peer's gossiped counter cells are rejected at merge time for being timestamped further than 5 seconds (`FUTURE_SKEW_TOLERANCE_SECS`) ahead of this node's clock. Wired via `CounterStore::with_skew_rejection_counter`, called from `ClusterCoordinator` construction in [`coordinator.rs`](../crates/lb-cluster/src/coordinator.rs). See the cardinality note above for the `peer` label's 64-peer bound and `other` overflow value.

### `lb_cluster_peer_sync_total` — counter

Labels: `peer`, `outcome`.

Incremented once per message or connection outcome on the gossip receive path ([`gossip.rs`](../crates/lb-cluster/src/gossip.rs)). `outcome` is `merged` (an authenticated message was applied), `own_node_id` (a peer announced this node's own `node_id`), `auth_failed` (the HMAC tag did not verify), `bad_frame` (a malformed or oversized frame) or `timeout` (no complete frame within the read timeout). A peer closing its connection after pushing is a normal end of stream and is not counted. `peer` is the sender's IP when it is one of the configured `cluster.peers`, and `unknown` otherwise, so connections from arbitrary addresses cannot grow the label set.

### `lb_cluster_auth_failures_total` — counter

Labels: `peer`.

Incremented whenever a gossip message fails HMAC verification, alongside a `warn`-level log line. `peer` follows the same bounded rule as `lb_cluster_peer_sync_total`: a configured peer's IP, or `unknown`. A non-zero rate means a misconfigured shared secret or someone probing the peer port.

### `lb_cluster_tracked_keys` — gauge

No labels.

Set on every gossip sync tick to the number of distinct keys in this node's cluster counter store, which is capped at `MAX_TRACKED_KEYS` (100,000).

## TLS and certificates

See [`tls.md`](tls.md) for the handshake, SNI resolution, and certificate reload mechanisms.

### `lb_tls_handshakes_total` — counter

Labels: `listener`, `outcome` (`success` | `failed` | `timeout`).

Incremented from the TLS-accepting connection path in [`lib.rs`](../crates/lb-server/src/lib.rs) (search for `tls_handshakes_success` / `_failed` / `_timeout`). `failed` covers a client-side handshake error (bad cert, protocol mismatch, or a probe); `timeout` covers a handshake that never completed within the handshake deadline; `success` is a completed handshake. The SNI hostname the client requested is deliberately never a label, since it is entirely client-controlled.

### `lb_tls_handshake_duration_seconds` — histogram

Labels: `listener`.

Observed for successful handshakes on the same code path as above, sharing the request-latency bucket set. A failed or timed-out handshake never becomes a request and is not represented in `lb_request_duration_seconds`, which is why this histogram exists separately.

### `lb_tls_certificate_reloads_total` — counter

Labels: `listener`, `outcome` (`applied` | `unchanged` | `rejected`).

Incremented once per reload tick from `spawn_reloader` in [`reload.rs`](../crates/lb-tls/src/reload.rs): `applied` when a changed, valid certificate/key pair was loaded and swapped in; `unchanged` when the tick found no file changes; `rejected` when a changed file failed to parse or validate — in which case the previous certificate stays in the resolver and the reload task keeps running rather than treating this as fatal. A rising `rejected` count while a certificate ages toward expiry is a rollout failure that would otherwise stay silent until the certificate expired.

### `lb_tls_certificate_expiry_timestamp_seconds` — gauge

Labels: `listener`, `cert`.

Set, on every `applied` reload tick (not on `unchanged` or `rejected` ticks), to each loaded certificate's `notAfter` as a Unix timestamp. Both `listener` and `cert` are carried because a certificate name is operator-chosen per `[[listeners.tls.certificates]]` entry and is not guaranteed unique across listeners; without the `listener` label two listeners reusing the same certificate name would silently overwrite each other's gauge value.

### `lb_backend_tls_verification_disabled` — gauge

Labels: `listener`.

Set to `1` for a listener whose backend-facing TLS client has certificate verification disabled (`danger_accept_invalid_certs`), and `0` otherwise, at wiring time in [`wiring.rs`](../crates/lb-server/src/wiring.rs). Exists so a dangerous configuration shows up on a dashboard instead of only in a config file that nobody re-reads.

## Response cache

See [`http-features.md`](http-features.md) for cache-key composition and TTL rules.

### `lb_cache_result_total` — counter

Labels: `listener`, `result` (`hit` | `miss`).

Incremented in `lb_proxy::service::handle_inner`: `hit` when a `GET` request's cache key is found and served from the response cache without touching a backend; `miss` when caching is configured for the listener but the key was not found (the request then proceeds to backend selection as normal). Only ever recorded when `[listeners.cache]` is configured and the request method is `GET`. There is no cache-eviction, cache-size, or cache-entry-count metric.

## WAF

See [`edge-hardening.md`](edge-hardening.md) for the built-in rule set.

### `lb_waf_blocked_total` — counter

Labels: `listener`, `rule` (`sql_injection` | `xss` | `path_traversal`).

Incremented in `handle_inner` whenever a built-in WAF rule matches the request path/query (or, if `inspect_headers` is enabled, an inspected header) — regardless of whether the listener's WAF mode is `block` or `log`. Only `block` mode actually returns `403 Forbidden`; `log` mode still increments this counter and falls through to normal handling. The counter alone cannot distinguish which mode produced a given increment — check the listener's configured mode, or the accompanying `tracing::warn!` log line, for that.

## WebSocket / Upgrade proxying

### `lb_websocket_upgrades_total` — counter

Labels: `listener`, `result` (`success` | `backend_declined` | `backend_unreachable`).

Incremented in [`upgrade.rs`](../crates/lb-proxy/src/upgrade.rs): `backend_unreachable` when connecting to or sending the request to the backend times out or fails outright; `backend_declined` when the backend responds without `101 Switching Protocols` (it doesn't support the upgrade); `success` once the backend has answered `101` and both sides of the tunnel are about to be spliced.

## Retries

See [`load-balancing.md`](load-balancing.md#retries-and-backend-selection) for the retry/idempotency rules and [`rate-limiting.md`](rate-limiting.md#retry-budget) for the retry budget. All six counters below share the label `listener` only, and are incremented from the single retry loop in `lb_proxy::service::handle_inner` (at most one retry is ever attempted per request):

| Metric | Incremented when |
|---|---|
| `lb_retry_attempts_total` | The first attempt failed (connect error or timeout), the method is idempotent, and a retry budget (if configured) admitted the retry — i.e., a second attempt is about to be made. |
| `lb_retry_successes_total` | The second (retry) attempt succeeded. |
| `lb_retry_failures_total` | The second (retry) attempt also failed. |
| `lb_retry_not_idempotent_total` | The first attempt failed but the request method is not idempotent, so no retry is attempted. |
| `lb_retry_budget_admits_total` | A configured retry budget allowed the retry. |
| `lb_retry_budget_denials_total` | A configured retry budget denied the retry (no second attempt is made). |

All six are counters (`IntCounterVec`). Note that `lb_retry_failures_total` and `lb_retry_successes_total` only ever fire on the retry (second) attempt — a first-attempt failure that is never retried (denied by budget, or non-idempotent) shows up only as `lb_backend_requests_total{outcome=...}` and one of `lb_retry_not_idempotent_total` / `lb_retry_budget_denials_total`, never as a "failure."

## Admin API

See [`operations.md`](operations.md) for the admin listener's routes and authentication model.

### `lb_admin_auth_disabled` — gauge

No labels.

Set once at startup in [`lib.rs`](../crates/lb-server/src/lib.rs) to `1` if the admin listener has no bearer token configured, `0` otherwise. Exists for the same reason `lb_backend_tls_verification_disabled` does: an open admin port (which exposes `/metrics`, `/healthz`, `/ready`, and backend drain/undrain) must show up on a dashboard, not just as a log line at startup.

### `lb_admin_auth_failures_total` — counter

No labels.

Incremented in [`admin.rs`](../crates/lb-metrics/src/admin.rs)'s `route` function whenever a request to the admin listener is missing its `Authorization: Bearer <token>` header or presents the wrong token (compared in constant time). Only meaningful when an admin token is configured; with no token configured, every request is accepted and this counter never increments.

## Suggested alerts

The following use only metrics confirmed live above. Adjust listener/job label matchers to your scrape config.

**No eligible backend for a listener** (approximate — based on the active health check only; a backend can be `healthy=1` and still be circuit-open or outlier-ejected, so treat this as a lower bound on outage severity):

```promql
sum by (listener) (lb_backend_healthy) == 0
```

**All backends in a listener have their circuit open:**

```promql
count by (listener) (lb_backend_circuit_state == 1)
  == count by (listener) (lb_backend_circuit_state)
```

**A circuit breaker is open right now** (page-worthy at low severity, since traffic is being actively excluded from that backend):

```promql
lb_backend_circuit_state == 1
```

**Certificate expiring within 14 days:**

```promql
(lb_tls_certificate_expiry_timestamp_seconds - time()) < 14 * 86400
```

**Cluster clock-skew rejections occurring** (a peer's clock is far enough ahead that its gossiped counters are being dropped — the cluster-wide rate limit is silently under-protecting on that peer's traffic):

```promql
rate(lb_cluster_future_skew_rejections_total[5m]) > 0
```

**Admin API left open with no token** (config drift on a sensitive listener):

```promql
lb_admin_auth_disabled == 1
```

**Backend TLS verification disabled** (encrypted but unauthenticated backend traffic):

```promql
lb_backend_tls_verification_disabled == 1
```

**Elevated 5xx rate:**

```promql
sum by (listener) (rate(lb_requests_total{status="5xx"}[5m]))
  / sum by (listener) (rate(lb_requests_total[5m])) > 0.05
```

**Cluster peer authentication failing** (mismatched shared secret, or probing of the peer port):

```promql
rate(lb_cluster_auth_failures_total[5m]) > 0
```

**A listener's rate-limit key table is full** (new clients are sharing the overflow bucket):

```promql
lb_ratelimit_tracked_keys >= 100000
```
